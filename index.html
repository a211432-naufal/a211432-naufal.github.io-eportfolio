Securing MyFood, one vulnerability at a time

MyFood is an SDG 2 (Zero Hunger) mobile app that connects people with surplus food to people in need. This project secures the app by finding and fixing vulnerabilities in login, data storage, communication, search, input handling and access control.

Projects

MyFood

Problem statement: Food is wasted while people go hungry, and apps that connect donors and receivers can expose users to attacks if they are not built securely. MyFood addresses this by sharing surplus food under SDG 2 while applying secure coding fixes to protect user accounts and data.

View on GitHub

Vulnerability solutions

Case 1: Login test

Live code vulnerability implementation of weak password storage and its fix.

I learned that storing plain-text passwords and accepting weak ones makes accounts easy to break into. Adding a password policy, salted hashing and account lockout made brute-force attacks much harder.

Case 2: Data 1

Live code vulnerability implementation of sensitive data stored in plain text.

I saw that anyone who can reach the device files could read the phone number and address stored in plain text. Using EncryptedSharedPreferences kept the data unreadable even when I opened the file directly.

Case 3: Data 2

Live code vulnerability implementation of insecure communication and a hard-coded key.

I realised that using http and a key written in the source code exposes secrets to anyone who reads the code or the network traffic. Moving the key to local.properties and using https protected both the key and the data while it travels.

Case 4: SQL injection

Live code vulnerability implementation of a search query built from raw input.

I saw that building a query from raw user input let me reveal private data with a simple input like ' OR 1=1 --. Using parameterised queries treated the input as plain text, so the same attack no longer worked.

Case 5: Input validation

Live code vulnerability implementation of unchecked user input.

I learned that accepting any input, such as empty titles, script tags or negative quantities, can break the app or open the door to attacks. Validating length, characters and ranges made sure only safe, sensible data was saved.

Case 6: Access control

Live code vulnerability implementation of deleting posts without an ownership check.

I found out that without an ownership check, any logged-in user could delete another user's post. Allowing only the owner or an admin to delete stopped unauthorised actions.

Reflection and learning journey

Through the MyFood project, I learned that security problems often come from small mistakes, such as storing passwords in plain text, trusting user input, or leaving a secret key in the code. By building each vulnerability first and then attacking it myself, I understood how easily these weaknesses can be exploited and why secure coding matters from the start.

Applying the fixes (password hashing, encrypted storage, HTTPS, parameterised queries, input validation and access control) showed me that most of them are simple to add once I know the risk. This project changed how I think about development: I now write code with security in mind instead of treating it as something to add at the end.
